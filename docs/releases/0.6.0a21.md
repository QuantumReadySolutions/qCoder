# qCoder 0.6.0a21

**Historical do-not-publish candidate.** qCoder 0.6.0a21 is immutable, unpublished, technically
qualified, rejected for publication truth, terminal, and must not be published. Its source and
distribution bytes remain historical evidence and must not be repaired, rebuilt, replaced,
tagged, published, or selected again.

qCoder 0.6.0a21 preserved the runtime implementation and product behavior of the immutable,
unpublished qCoder 0.6.0a20 candidate. It would have been a behavior-changing pre-release
successor to public qCoder 0.6.0a18, but it was never published. Its release note incorrectly
described behavior preservation as relative to public a18; that publication-truth defect consumed
the a21 identity. Public upgrade lineage and implementation lineage are distinct.

Routine Current Loop source work retains one terminal-closure route in the exact bounded action.
When an exact native-edit integration is configured, a successful native edit drives qCoder's
independent validation, single registration, receipt, and source-stage stop without a redundant
completion call or another interpretation of qCoder procedure. Hook-absent clients keep the same
fail-closed typed-completion route, authority ceiling, postcondition checks, registration, state
transition, and recovery semantics.

The release preserves exact-message and current-step authority, client-owned native mutation,
process-and-discard privacy, immutable history, causal currentness, strict result manifests,
no-rerun recovery, and idempotent duplicate handling. A source-only request does not authorize
QASM, execution, results, review, unrelated artifacts, or forced Current Loop closure.

Exactly twelve public Context Bridge tools and the two private coordination operations remain.
qCoder gains no authority to generate or edit customer source, execute a simulator, runtime, or
hardware job, retain customer artifacts, discover a repository, or activate native-client
authority. Binding and adapter conformance do not by themselves establish qualification for any
client, client version, operating environment, topology, or workstyle.

## Upgrading from qCoder 0.6.0a18

Install qCoder 0.6.0a21 for a new installation or before starting a new Current Loop. If qCoder
0.6.0a18 already has an active Current Loop, upgrade only at a clean Current Loop boundary: before
a new loop begins or after the current loop has reached a truthful terminal boundary.

Do not upgrade while any binding v44 / Current Step Contract v10 step, completion, continuation
capsule, pending receipt, or recovery action remains outstanding. Finish the outstanding step on
qCoder 0.6.0a18, or explicitly abandon it and restart the work under qCoder 0.6.0a21 at a clean
boundary.

qCoder does not support or claim mid-step migration from binding v44 / Current Step Contract v10
to binding v45 / Current Step Contract v11. A v44/v10 operation receipt, authority grant,
completion input, continuation capsule, or pending step must not be reused or reinterpreted under
v45/v11. Project evidence history may remain; this boundary applies to the active step.

This release makes no latency or quiet-operation guarantee, does not establish universal framework
neutrality, general framework qualification, or general PennyLane qualification, and does not
activate Tested, First-class, Client Compatibility, or another public support claim. Publication,
deployment, and qualification remain separate lifecycle decisions.
